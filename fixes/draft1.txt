Post-Quantum Cryptography & SecureMark-TLS Profiles on Embedded Microcontrollers

1 Experimental Environments and Hardware Measurement Setup

To evaluate post-quantum cryptographic workloads against classical TLS primitives on resource-constrained edge
hardware, two target microcontrollers representing modern Cortex-M and Xtensa architectures were configured:
 NXP FRDM-MCXN947 Target: Dual ARM Cortex-M33 cores operating at 150 MHz (ARMv8-M Mainline

   with TrustZone and DSP extensions), equipped with 2 MB dual-bank Flash, 512 KB SRAM, and an on-chip
   eIQ Neutron NPU with dedicated DMA bus routing. Toolchain: arm-none-eabi-gcc v13.2.1 with flags -O2
   (speed) and -Os (SIZE OPTIMIZATIONS), -mcpu=cortex-m33+nodsp, -mfpu=fpv5-sp-d16, -mfloat-abi=hard.
   Operating environment: Zephyr RTOS v4.2.0-rc1.
 ESP32-S3 DevKitC Target: Dual Xtensa LX7 cores operating at 240 MHz, with 8 MB Octal SPI Flash and
   512 KB SRAM. Toolchain: xtensa-esp32s3-elf-gcc v12.2.0 with flags -Os and comparative -O2. Operating
   environment: ESP-IDF v5.1 / Zephyr RTOS v4.2.0-rc1.

1.1 Instrumentation Methodology

 Execution Cycles & Latency: Measured directly via internal hardware registers using the ARM Data
   Watchpoint and Trace (DWT) CYCCNT cycle counter on the MCXN947 and the Xtensa CCOUNT register on
   the ESP32-S3. All tests were executed in free-running mode with debuggers and UART streams detached to
   eliminate clock jitter.

 Dynamic Stack Memory High-Water Mark (HWM): Stack memory regions were pre-painted at boot
   with a distinct byte pattern (0xEE). Following execution, stack memory boundaries were scanned using
   k threadstack space gettorecordtheexactpeakbyteusage.Active Power & Energy Profiling:CapturedusingaN ordicP o

 Sample Size: 100 repetitions per KEM operation and 2,000 repetitions per DSA operation, yielding standard
   deviations under 0.5%.

2 Bare-Metal EEMBC SecureMark-TLS Classical Profile

The classical baseline was established using the self-hosted EEMBC SecureMark-TLS benchmark suite, running
mbedTLS (v3.6.3 on MCXN947; ESP-IDF mbedTLS on ESP32-S3) across 14 cryptographic phases modeling a
TLS 1.2 handshake (ECDH P-256, ECDSA P-256, AES-128-CBC/CCM, SHA-256).
 NXP FRDM-MCXN947 Score (-O2): 5,472.08 SecureMark Marks (Passed 14/14 CRC component

   validations; file: securemark score.txt).
 ESP32-S3 DevKitC Score (-Os): 1,895.06 SecureMark Marks (Passed 14/14 CRC component valida-

   tions; file: securemark esp32s3 score.txt).

2.1 Low-Level Porting Adjustments

1. ECP Point Blinding PRNG: Implemented a lightweight xorshift pseudo-random generator to feed
   mbedTLS point blinding, preventing null-pointer MBEDTLS ERR ECP BAD INPUT DATA aborts.

2. SEC1 Public Key Header Formatting: Dynamically prepended the SEC1 0x04 byte to raw 64-byte X||Y
   EEMBC public key arrays before passing them to mbedTLS parsing functions.

3. ASN.1 DER Signature Formatting: Formatted raw r||s hardware signature registers into standard DER
   structures required for EEMBC CRC verification.

6 Single-Core Sliced Cooperative Scheduling and Obfuscation

To execute post-quantum handshakes alongside a 30 FPS (33.3 ms frame budget) real-time control loop on a
single CPU core:
 Cooperative Handshake Slicing: Handshakes are divided into non-blocking operational chunks executed

   during available frame timing slack. This reduces real-time control deadline misses from 10.0% down to
   0.0% while reducing CPU execution footprint by 14-15%.
 Side-Channel Power Obfuscation: Inserting probabilistic dummy-state calculations (p = 0.3) into idle
   timing slack masks 10 kHz power-envelope activity leakage, degrading an attacker's side-channel classification
   accuracy from 100% down to 75.5%.

7 Codebase Organization and Execution Commands

All experiment source code, hardware drivers, and evaluation scripts are structured within the repository as
follows:
 codebase/projects/securemark tls mcxn947/: Bare-metal MCXN947 SecureMark-TLS C driver, mbedTLS

   wrappers, and migration compare.py.
 codebase/projects/securemark tls esp32s3/: ESP32-S3 ESP-IDF SecureMark-TLS C driver and cross platform comp
 codebase/mlkem bench/ & mldsa bench nxp/: Bare-metal cycle counter drivers (dwt.h), stack painting

   scripts, and raw PQC datasets.
 codebase/knowledge/: Raw CSV benchmark logs (dtls cid daily energy.csv, mlkem perf memory summary.csv,

   mldsa87 sign raw.csv).
