# X25519 Benchmark Methodology

Companion to `mlkem_bench`'s `BENCHMARK_METHODOLOGY.md` — same board,
same techniques (DWT cycle counter, stack painting, GPIO-triggered
energy mode, PPK2 at J24), so results are directly comparable. This
doc only covers what's specific to X25519.

## 1. Why X25519, and which implementation

X25519 is the classical (pre-quantum) elliptic-curve Diffie-Hellman
scheme it's meant to be compared against — TLS 1.3 and most current
key-exchange deployments use it today. Benchmarking it on the same
board with the same methodology gives a concrete "what does moving to
post-quantum cost" number, rather than relying on numbers from a
different paper's different hardware/methodology.

**Implementation history, for the record**: TweetNaCl's `crypto_scalarmult`
was tried first (extracted to just the field arithmetic + scalarmult,
~150 lines) and produces a genuinely tiny binary (~21 KB flash) — but
TweetNaCl is deliberately optimized for minimal code size, not speed
(its own stated design goal), using a naive schoolbook field
multiplication. It measured at ~717ms/operation, about 36x slower than
ML-KEM-512 — not representative of typical X25519 performance, and
would have made for a misleading comparison. Swapped to
**curve25519-donna** (Google/Adam Langley, BSD-3-Clause, portable
32-bit-friendly radix-25.5/26 field arithmetic) instead — the standard
choice for a "portable reference, not hand-optimized" X25519
benchmark, same tier of implementation as PQClean's `clean` for
ML-KEM. This produces a larger binary (~47 KB flash, actually somewhat
larger than ML-KEM's ~42 KB) but a much more representative ~141.5ms
per operation.

Both implementations are kept in git history / this note for
transparency; only the donna-based numbers are reported as the
headline result.

## 2. Operation structure differs from ML-KEM — a real difference, not an inconsistency

X25519 is a Diffie-Hellman scheme, not a KEM, so it has no
encaps/decaps split. Both parties in a real exchange run the same two
operations:

1. **keypair**: `crypto_scalarmult_base` — generate a private/public keypair
2. **shared_secret**: `crypto_scalarmult` — compute the shared secret
   from your private key and the peer's public key

A full exchange from one party's perspective is therefore these two
operations once each — **two operations total**, versus ML-KEM's three
(keypair/encaps/decaps). This is a structural property of DH vs. KEM
schemes, not a measurement shortcut, and is called out explicitly
wherever these numbers are compared.

Both operations cost virtually the same (~21.2 million cycles each) —
expected, since `crypto_scalarmult_base` is `crypto_scalarmult` called
with a fixed base point; the 255-iteration Montgomery ladder runs the
identical number of steps regardless of which point is supplied.

## 3. Determinism

Every repetition (100 requested; 96 usable in the capture on record —
see `results/eembc_style/analyze_perf_memory.py`'s note) produced
bit-for-bit identical cycle counts. This is expected: the Montgomery
ladder is a fixed-length, branchless computation with no
secret-dependent branching (a deliberate constant-time design property,
same rationale as the `swap_conditional` function in the source),
so unlike ML-KEM there is no cycle-level jitter to average over.
