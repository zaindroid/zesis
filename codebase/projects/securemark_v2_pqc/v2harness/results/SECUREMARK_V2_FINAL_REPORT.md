# SecureMark-V2 with PQC suites — consolidated results

**Board:** FRDM-MCXN947, Cortex-M33 @ 150 MHz, bare metal (no RTOS, no debugger).
**Optimisation level: `-O2` for every primitive, PQC and classical alike.** This
is the single stated methodology level for every comparison number below;
`sensitivity to the level` is quantified at the end.
**Timing:** DWT cycle counter (`DWT->CYCCNT`), 64-bit accumulated.
**Backend:** wolfSSL 5.9.2, native `wc_mlkem.c` / `wc_mldsa.c`, crypto-only
(`WOLFCRYPT_ONLY`), `WOLFSSL_NO_ASM`.

## 2. Handshake: PQC vs classical, same library, same flags

Both sides wolfSSL at `-O2`. Public-key phase = 1 ECDH + 1 sign + 2 verifies.

| Handshake public-key phase | Component times | Total |
|---|---|---|
| Classical (P-256) | 24.34 (ECDH) + 17.57 (sign) + 2 x 26.50 (verify) | **94.91 ms** |
| PQC (ML-KEM-768 + ML-DSA-65) | 6.37 (enc) + 8.24 (dec) + 60.36 (sign) + 24.57 (verify) | **99.54 ms** |

**The PQC public-key phase is 4.9% more expensive than classical P-256.**

This corrects an earlier figure of "-3.6% cheaper". That number came from a
3-iteration ML-DSA-65 sign mean; with a 30-iteration mean the sign cost rises
from 52.33 to 60.36 ms and the sign flips. The de-noising was worth doing for
exactly this reason. The qualitative picture is unchanged: the PQC penalty on
this workload is a few percent, not the +83% an mbedTLS-based classical
comparison at `-O2` once suggested, and the cost is concentrated in signing
(60.36 ms) while PQC encapsulation and key establishment are far cheaper than
their classical counterparts.

## 3. Task 3A — 128 KB firmware signature verification (secure boot)

Firmware: `task3a/`. Payload 131,072 B, all four schemes verify PASS.
Capture: `task3a/results/task3a_raw.txt`.

| Scheme | pre-hash | sign | **verify** | sig bytes | end-to-end | payload RAM |
|---|---|---|---|---|---|---|
| ECDSA P-256 | 44.23 | 16.93 | **26.73 ms** | 71 | 70.96 ms | streamed |
| ML-DSA-44 pure | n/a | 190.0 | **133.10 ms** | 2420 | 133.10 ms | **131,072 B** |
| ML-DSA-65 pure | n/a | 202.4 | **143.13 ms** | 3309 | 143.13 ms | **131,072 B** |
| HashML-DSA-65 | 85.34 | 57.49 | **24.45 ms** | 3309 | 109.79 ms | streamed |

(ms. pre-hash = streaming SHA-256 / SHA-512 over the 128 KB in 4 KB chunks.)

Findings:

1. **Hashing dominates pure ML-DSA verification.** ML-DSA-65 verify (143 ms)
   absorbs a SHAKE256 pass over 128 KB inside the primitive. Pre-hashing lifts
   it out: HashML-DSA-65 verifies a 64-byte digest in **24.45 ms**, 5.9x faster,
   and is 23% cheaper end-to-end than the pure path.
2. **HashML-DSA-65 verification beats ECDSA P-256 verification:** 24.45 vs
   26.73 ms. The classical advantage sits in the pre-hash and the signature size,
   not in verification.
3. **The buffering split is asymmetric.** Pure ML-DSA requires the whole payload
   addressable at once — **131,072 B of RAM** for a device receiving firmware
   over a link. ECDSA and HashML-DSA verify a digest and stream the payload in
   4 KB chunks: 112 B (SHA-256) or 224 B (SHA-512) of context plus a 4 KB chunk.
4. **Signature overhead:** 71 B (DER ECDSA) vs 2420 (ML-DSA-44) vs 3309
   (ML-DSA-65 / HashML-DSA-65) — a 34-47x larger header.

## 6. Caveats — all of them, in one place

**Evidence standard for PQC.**
1. EEMBC has published no PQC profile, so there is **no EEMBC golden CRC** for
   ML-KEM or ML-DSA. Those suites are reported under a dual scheme: a functional
   round-trip self-check (KEM decapsulation recovers the shared secret; DSA
   verification returns valid) plus a **synthesized regression CRC** over the
   deterministic output. "EEMBC CRC MATCH" is never claimed for them. The
   classical suites remain the only ones checked against EEMBC goldens.

**Task 3A specifically.**
2. **SHA-256 and SHA-512 are software implementations** (`WOLFSSL_NO_ASM`), so
   the 44.23 ms and 85.34 ms pre-hash figures are pessimistic for the classical
   side. A hardware hash engine would cut them substantially and would shift the
   end-to-end ranking, though not the verify-only comparison.
3. Task 3A is one run per scheme. The sign column is a single draw; the verify
   column is stable because verification has no rejection loop.
4. `wc_ecc_verify_hash` takes `(sig, siglen, hash, hashlen, res, key)`. The first
   Task 3A run had the arguments reversed and reported a spurious FAIL at 0 ms.
   Corrected, and worth recording because the failure mode was quiet.

**Measurement.**

5. ML-DSA signing is rejection sampled. Its distribution over 2000 runs at 256 B
   has a worst/median ratio of 6.6x / 6.9x / 4.8x for levels 44 / 65 / 87, so a
   single draw can land anywhere. Use the n=2000 distributions for tails; the
   harness figures are 30-iteration means.
6. The harness's `ips` is iterations over elapsed time, so PQC components are
   means, not draws. The count was raised from 3 to 30 for this report; the
   earlier 3-iteration mean was optimistic by ~13% on ML-DSA-65 sign.

**Build configuration.**

7. `WOLFSSL_NO_ASM` throughout. The `--enable-sp` / assembly build is a separate
   library variant and will move these numbers.
8. Historical rows in the matrix carry different flags (`-O0`, `-Os`) and are
   labelled as such; only the `-O2` rows are comparison-grade.
9. RSA-4096 required `SP_INT_BITS 4096` (`RSA_MAX_SIZE` derives from it).
   Without that, the classical Heavy suite fails and the run aborts.
10. The harness's `AUTOTUNE` loop was bounded (24 doublings). Upstream, a
    component that fails instantly never reaches the 1 s tuning target and spins
    forever, so the score section never prints. This is a **harness change**.
11. Three upstream warnings are downgraded, not fixed
    (`-Wno-error=format`, `maybe-uninitialized`, `incompatible-pointer-types`;
    the last is a `word32`/`uint32_t` spelling difference with identical layout).
    **My four files (`ee_pqc.c`, `th_pqc_support.c`, `th_mlkem.c`, `th_mldsa.c`)
    are warning-clean under `-Wall -Wextra`** — the only diagnostic they raise is
    wolfSSL's own advisory `#warning` about harden options.

**Scope.**

12. The pqm4 row is indicative: M4F assembly that does not run cleanly on the
    M33. Its post-mortem fault (`CFSR 0x00100000`) is `UFSR.STKOF` (stack
    overflow), not `UNSTKERR` — an ARMv8-M vs ARMv7-M bit-position difference.
13. `PQC_All` mixes keypair, encapsulation and validation with equal weight. The
    protocol-weighted score exists precisely because equal weighting is not how
    a handshake costs out.

## 8. Follow-ups closed

### 8.1 The assembly/SP variant does not exist for this target

The earlier caveat "`WOLFSSL_NO_ASM` throughout" implied the assembly build was
an option not taken. It is not an option. wolfSSL gates its Cortex-M SP assembly
on `WOLFSSL_ARM_ARCH_7M`, which is auto-detected from `__ARM_ARCH_7M__`:

```c
#if defined(WOLFSSL_SP_ARM_CORTEX_M_ASM) && defined(WOLFSSL_ARM_ARCH_7M)
```

The MCXN947 is ARMv8-M (Cortex-M33), so the gate is closed, and searching
`settings.h` for ARMv8-M assembly found no path. **Verified empirically:** removing
`WOLFSSL_NO_ASM` and rebuilding produces a byte-identical library (575,922 B),
because the macro was never the limiter. The flag is restored with this finding
recorded at the point of definition.

This is the same class of limitation as pqm4's, and it means the "embedded
engine" tier is portable C by necessity, not by choice.

### 8.2 pqm4 absolute numbers, and the result they produce

pqm4's ML-KEM-768 on this board (reset-loop capture, one operation per boot):

| ML-KEM-768 encapsulate | Implementation | Flags | Time | Cycles |
|---|---|---|---|---|
| 15.33 ms | PQClean clean C | -O2 | 15.33 ms | 2,299,500 |
| **6.37 ms** | **wolfSSL native** | **-O2** | **6.37 ms** | **955,000** |
| 23.99 ms | pqm4 (Cortex-M4F assembly) | -O3 | 23.99 ms | 3,598,500 |

**The hand-tuned assembly tier is the slowest of the three.** It is 1.6x faster
than the clean-C reference *it was measured against* (a differently-flagged
build), but at matched `-O2` it is 1.6x slower than PQClean clean C and 3.8x
slower than wolfSSL's portable native implementation. Its own numbers are
also incomplete: decapsulation and all of ML-DSA fault on the M33.

So the three-tier ordering the thesis expected — reference C < portable engine <
assembly — does not hold on this board. The correct statement is: **a modern
portable PQC implementation beat the M4F-specific assembly, which itself is not
fully portable to ARMv8-M.** That is a defensible and more interesting finding
than the expected one, and it is now in the matrix as measured absolute values.

### 8.3 Task 3A as distributions (n = 20 per scheme)

| Scheme | sign mean/min/max (ms) | verify mean/min/max (ms) | sig bytes |
|---|---|---|---|
| ECDSA P-256 | 16.93 / 16.93 / 16.93 | 26.70 / 26.70 / 26.70 | 72 |
| ML-DSA-44 pure | 155.72 / 137.42 / 217.14 | 133.10 / 133.10 / 133.10 | 2420 |
| ML-DSA-65 pure | 179.47 / 148.75 / 318.18 | 143.13 / 143.13 / 143.13 | 3309 |
| HashML-DSA-65 | 55.30 / 30.08 / 107.91 | 24.45 / 24.45 / 24.45 | 3309 |

This settles the "single draw" caveat:

- **Verification is deterministic.** Every scheme's verify min and max differ by
  under 0.1% (133.096-133.101 ms). There is no rejection loop, so the
  verify-only comparison — including HashML-DSA beats ECDSA — is stable.
- **Signing carries the tail.** In just 20 draws, HashML-DSA-65 sign spread from
  30.08 to 107.91 ms (3.6x) and ML-DSA-65 from 148.75 to 318.18 ms (2.1x).
  ECDSA sign is constant (16.93 ms) because deterministic k removes the
  randomness. Verify-only conclusions are safe; sign conclusions need the n=2000
  distributions.
- Two firmware bugs were found and fixed by the repeat loop, both of which a
  single-draw run hides: `wc_ecc_verify_hash` takes `(sig, siglen, hash, hashlen)`
  and the arguments were reversed; and `siglen` is an in/out parameter, so the
  second DER signature overflowed its buffer (`BUFFER_E`, -132) unless reset.
  A single run per scheme cannot surface either.
